## Objective

Extend `URLSessionHTTPClient.init()` with a `timeoutSeconds: TimeInterval = 8` parameter so Plan 04-08 (composition root) can construct a **second** instance with a 2-second timeout for localhost probes — implementing the POLL-08 timeout split (8s remote / 1–2s localhost) that's been on the books since Phase 1 STATE #18.

Per CLAUDE.md "Concurrency & Polling Pattern" + CONTEXT Discretion §"1–2s localhost timeout":
> A second `URLSessionHTTPClient(timeoutSeconds: 2)` instance injected via `AppDependencies.makeProduction()` preserves the "one session per app" rule **per-tier**. Remote (8s) and local (2s) are different `URLSession` instances by necessity per POLL-08 split.

The default of 8 preserves every existing Phase 1/2/3 call site verbatim — this is an additive parameter with a back-compat default. The only consumer of the new value is Plan 04-08's localhost-tier instance.

## Context

Phase 1 STATE #18 / `Infrastructure/URLSessionHTTPClient.swift:26-34` declares the production `URLSession` singleton with hard-coded 8s `timeoutIntervalForRequest`. Phase 4 cannot reuse this singleton for localhost probes because:

1. The 8s timeout would let a stalled `ollama serve` block a poll cycle for up to 8 seconds — visible in the menu bar as a frozen popover.
2. POLL-08 REQUIREMENT-level says "8s for remote APIs, 1–2s for localhost" — currently only the 8s side is exercised.
3. ROADMAP Phase 4 SC#1 explicitly says "Ollama row …refreshed on the standard 5-min cadence with a 1–2s connect timeout."

The "alternative" rejected in CONTEXT Discretion (per-request `URLRequest.timeoutInterval` override inside each local provider) leaks tier knowledge into provider code that should stay tier-agnostic. The chosen approach (RESEARCH §6.2): one `URLSessionHTTPClient` instance per tier.

Files referenced:
- `AgentsUsageBar/Infrastructure/URLSessionHTTPClient.swift:23-34` — production `init()`; line 28 hard-codes `cfg.timeoutIntervalForRequest = 8`.
- `AgentsUsageBar/Infrastructure/URLSessionHTTPClient.swift:36-43` — internal `init(session:)` test seam (preserve unchanged).
- `AgentsUsageBar/Infrastructure/URLSessionHTTPClient.swift:47-51` — `configurationSnapshot()` test seam (we'll reuse this in T-04-03-02 to verify the timeout value lands on the URLSession.configuration).

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Existing call site `URLSessionHTTPClient()` in `AppDependencies.makeProduction()` line 71 breaks | Default value `= 8` preserves byte-identical behavior; verified by `grep 'URLSessionHTTPClient()' AppDependencies.swift` returning ≥ 1 hit after this plan lands. |
| Resource-timeout scaling breaks a Phase 2/3 long-running endpoint (e.g. ClaudeOAuthClient refresh) | Scaling math is `max(timeoutSeconds * 4, 30)` — for the 8s tier this yields 32s, only 2s longer than the old hard-coded 30s. Phase 2/3 callers do not have requests that take 30+ seconds; no observable behavior change. Locked by `defaultInit_yieldsRemoteTier30sResource` test. |
| Two `URLSessionHTTPClient` instances accidentally share session state | URLSession is constructed fresh inside each `init()` via `URLSession(configuration: cfg)` — no shared backing store. Locked by `twoInstances_areDistinctURLSessions` test. |
| Localhost connections to a non-listening port timing out at 2s instead of immediately throwing `.cannotConnectToHost` | macOS Darwin loopback behavior: ECONNREFUSED on a not-listening port is returned synchronously by `connect(2)` — `URLError.cannotConnectToHost` fires in well under 100ms. The 2s timeout protects against a half-open socket or a process accept-loop stall, not against the normal "server's not running" case. RESEARCH §3.1 confirms this. |
| Test pollution: `URLSessionHTTPClient` instances accumulate undisposed sessions during parallel test runs | Each `URLSessionHTTPClient` is short-lived inside the test scope; `URLSession` is GC'd with the parent. Phase 1 `URLSessionHTTPClientTests` already demonstrates this pattern at scale (24+ tests). |
